# テスト計画

## 1. 目的・範囲

記録の追加・一覧・詳細・更新・削除、入力検証、天気API取得と障害時の分離を確認する。DBを使う統合テストは専用の開発用DBに限定し、天気APIテストはモック応答を基本とする。

## 2. 前提

- Node.js/Express APIとPostgreSQLのテスト環境が用意されている。
- 各テストの前後で作成したテストデータを整理できる。
- 日付・ID・任意項目を含む代表データを使用する。

## 3. 機能テスト

| ID | 対象 | 手順・入力 | 期待結果 |
|---|---|---|---|
| TC-01 | 一覧（空） | データ0件で一覧APIを呼ぶ | 200、空配列。画面は空状態メッセージを表示する。 |
| TC-02 | 追加（標準） | 必須項目と任意項目を送信 | 201。採番IDと入力値が返り、DBに保存される。 |
| TC-03 | 追加（任意項目なし） | 必須項目のみ送信 | 201。任意項目はnullとして保存・表示される。 |
| TC-04 | 一覧（複数件） | 異なる日付および同日データを登録して一覧取得 | 日付降順、同日ではID降順で返る。 |
| TC-05 | 詳細（存在） | 登録済みIDを指定 | 200。該当する1件だけ返る。 |
| TC-06 | 詳細（不存在） | 未登録IDを指定 | 404とNOT_FOUNDエラー。 |
| TC-07 | 更新 | 登録済みの全項目を変更してPUT | 200。変更値と更新日時が反映される。 |
| TC-08 | 更新（不存在） | 未登録IDへPUT | 404。別データは変更されない。 |
| TC-09 | 削除 | 登録済みIDをDELETE | 204。再取得は404、一覧にも含まれない。 |
| TC-10 | 削除（不存在） | 未登録IDをDELETE | 404。 |
| TC-11 | 手入力天気 | weatherに「小雨」などを指定 | 指定文字列をそのまま保存・取得できる。外部通信は発生しない。 |
| TC-12 | 今日の天気取得 | 都市タイムゾーンで今日の日付を指定 | `dataType=current`で現在天気・現在気温を返し、日別最高・最低気温は返さない。 |
| TC-13 | 過去の天気取得 | 過去日を指定 | `dataType=historical`で履歴天気・最高/最低気温・降水量を返す。 |
| TC-14 | 未来予報取得 | 予報範囲内の日付を指定 | `dataType=forecast`を明示し、対象日の予報を返す。 |
| TC-15 | 予報範囲外 | 15日先を超える日付を指定 | 422 FORECAST_OUT_OF_RANGE。外部APIへ不要な要求をしない。 |
| TC-16 | 履歴データ未提供 | 履歴APIに対象日のデータがない | 422 HISTORY_UNAVAILABLEと理由を返す。 |
| TC-17 | 都市なし | 検索結果のない都市名を指定 | 404 CITY_NOT_FOUND。DBアクセスは発生しない。 |
| TC-18 | 天気API障害 | タイムアウトまたは上流エラーを発生させる | 504または502。エラー後も記録CRUD APIが利用できる。 |
| TC-19 | 保存済み天気の再表示 | 天気入り記録を一覧で再取得 | 保存した天気文字列を表示し、天気APIを呼び直さない。 |
| TC-20 | 都市候補検索 | 日本語・英語・中国語の都市名を入力 | 候補に都市名・地域名・国名を表示し、同じ場所の重複は統合する。 |
| TC-21 | 候補入力操作 | 連続入力後に上下キー、Enter、Escapeを操作 | 約300msのデバウンス、選択と閉じる操作ができる。古い応答は表示しない。 |
| TC-22 | 選択地点の天気 | 候補を選択して天気を取得 | 候補の緯度・経度・タイムゾーンを使い、再ジオコーディングしない。 |
| TC-23 | 候補検索の障害 | 候補なし、タイムアウト、外部APIエラー | 分かりやすいメッセージを表示し、記録CRUDは利用できる。 |
| TC-24 | ページ付き一覧 | `page=2&limit=5`で一覧取得 | 所有者の記録だけを日付降順・同日ID降順で返し、`LIMIT/OFFSET`とページ情報を使う。 |
| TC-25 | ページ入力検証 | 0、文字列、不許可のlimit、大きすぎる値を指定 | 400 `INVALID_PAGINATION`。DBへ問い合わせない。 |
| TC-26 | 最終ページ補正 | 現在ページの記録を削除後、範囲外のpageを取得 | 最後に存在するページ番号へ補正して返す。 |
| TC-27 | 旧一覧API互換性 | クエリなしの`GET /api/trips`を呼ぶ | 従来どおり配列を返す。 |

## 4. 入力検証テスト

| ID | 入力 | 期待結果 |
|---|---|---|
| TV-01 | outingDate欠落 | 400、検証エラー。保存されない。 |
| TV-02 | outingDateを不正形式または存在しない日付にする | 400、検証エラー。 |
| TV-03 | cityまたはdestination欠落・空白のみ | 400、該当項目が示される。 |
| TV-04 | city、destination、weatherの上限超過 | 400。DBエラーではなく入力エラーとして返る。 |
| TV-05 | 数値でない、0、負数のID | 400。 |
| TV-06 | SQL風の文字列を通常フィールドに入力 | SQLとして実行されず、データとして安全に扱われる。 |
| TV-07 | HTML/スクリプト文字列をactivity等に入力 | APIでは文字列として保存され、画面では実行されずエスケープ表示される。 |
| TV-08 | PUTで必須項目を欠落 | 400。既存データを部分的に変更しない。 |

## 5. DB・エラー処理テスト

| ID | 条件 | 期待結果 |
|---|---|---|
| TD-01 | 作成後にDBから値を確認 | 日付、文字列、null項目が設計どおり保存される。 |
| TD-02 | 更新後にDBから値を確認 | `updated_at`が更新され、`created_at`は維持される。 |
| TD-03 | DB接続失敗 | APIは適切な5xx応答を返し、内部接続情報を利用者へ露出しない。 |
| TD-04 | エラー応答形式確認 | エラーコード・メッセージが一貫し、SQLやスタックトレースを含まない。 |

## 6. 画面確認

- 一覧、詳細、登録、編集の各画面から主要操作を行える。
- 必須項目エラーとサーバーエラーを利用者が理解できる形で表示する。
- 削除前に対象が分かる確認表示を行い、キャンセル時は削除されない。
- 空状態、長い活動内容、天気未入力でもレイアウトが崩れない。
- 天気検索、天気入力、活動内容の順で表示し、スマートフォン幅でも操作しやすい。
- ページサイズ変更、前へ・次へ、ページ番号移動と境界ボタンの無効化を確認する。

## 7. Google認証・所有者分離

| ID | 条件 | 期待結果 |
|---|---|---|
| TA-01 | 正常なOIDC callback | state、nonce、PKCEを確認し、Google `sub`でusersを作成または更新し、セッションを再発行する。 |
| TA-02 | stateまたはnonceが不一致 | ログインを拒否し、users登録とセッション作成をしない。 |
| TA-03 | `email_verified`がfalse | ログインを拒否する。 |
| TA-04 | 未ログインで記録・天気APIを呼ぶ | 401。DB上の出行記録を返さない。 |
| TA-05 | 他ユーザーの記録IDで詳細・更新・削除 | 404で、行を変更・削除しない。 |
| TA-06 | POST/PUT/DELETE/ログアウトでCSRF token欠落・不一致 | 403。DB query・セッション破棄を行わない。 |
| TA-07 | 正常ログアウト後に同じCookieでAPIを呼ぶ | セッションが無効となり401。 |
| TA-08 | user_idがNULLの既存行 | DBから削除・更新されず、一般の一覧・詳細APIには表示されない。 |
| TA-09 | 明示的な既存行割当SQL | 選んだ既存users.idへNULL行だけを割り当て、記録の他カラムを変えない。 |

OAuth callback、セッション発行、行所有者分離はモックで自動テストする。マイグレーションのデータ保持確認は専用テストDBで行い、実利用DBでは実行しない。

## 8. メールリマインダー

| ID | 条件 | 期待結果 |
|---|---|---|
| TR-01 | 未来日の記録を通知オフで登録 | 記録は保存し、通知ジョブを作らない。 |
| TR-02 | 8日以上先の予定を通知オンで登録 | pendingジョブの予定時刻が7日前10:00 JSTとなり、期限前のワーカー実行では送信しない。 |
| TR-03 | 7日前10:00 JSTの境界時刻にワーカーを実行 | 対象ユーザーの確認済みメールへ、日付・目的地・活動内容を送信し、履歴をsentにする。 |
| TR-04 | 7日未満の未来予定を通知オンで登録 | 既に通知予定時刻が過ぎていればmissedとし、自動送信しない。 |
| TR-05 | 過去日または東京時間で今日の予定を通知オンにする | API検証で拒否する。 |
| TR-06 | 予定日を変更 | 未送信ジョブを新しい日付から再計算する。送信済みジョブは再送しない。 |
| TR-07 | 通知を無効化または記録削除 | 未送信ジョブをキャンセルし、履歴は保持する。 |
| TR-08 | 同一ジョブを複数ワーカーが同時処理 | `SKIP LOCKED`と一意な試行番号により同一試行を二重claimしない。 |
| TR-09 | SMTP送信失敗 | 安全なエラーコードと履歴を保存し、最大5回・規定間隔で再試行する。認証情報をログに出さない。 |
| TR-10 | メール送信後DB更新失敗 | SMTPのみでexactly-onceは保証できないことを踏まえ、未知状態・安定Message-IDを残して運用調査できる。 |
| TR-11 | ワーカー停止後24時間以内に再実行 | 未処理ジョブを回復し、期限到来分だけを処理する。 |
| TR-12 | 予定時刻から24時間超過後に再実行 | 未処理ジョブをmissedにし、古い通知を送らない。 |
| TR-13 | 別ユーザー、未確認メール、通知無効の記録 | 送信対象に含めない。 |

自動テストは注入時計、モックメール送信、モックリポジトリで実施し、実DB・外部SMTPは使わない。PostgreSQLの実行計画・同時ロックとMailpit受信確認は専用開発環境で手動確認する。
